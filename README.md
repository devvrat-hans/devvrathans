# devvrathans.com

Personal site for Devvrat Hans, in two versions:

| Version | Pages | For | Email shown |
|---|---|---|---|
| **Portfolio** | `/`, `/resume` | Recruiters and hiring: experience, projects, skills, resume/CV, GitHub heatmap | devvrat.coding@gmail.com |
| **Real me** | `/me`, `/blog`, `/notes`, `/newsletter`, `/x` | Building Aback in public: the journey, products, writing, notes from Notion, a biweekly newsletter, X sponsorship rates | devvrat@aback.ai |

A switch next to the logo moves between them. A page belongs to a version by its path alone
(`sideForPath` in `src/lib/site.ts`), so the nav links, footer, command palette and the email shown
all follow along.

Static Next.js export deployed to Cloudflare Pages, plus a small Cloudflare Worker that keeps the
heatmap data fresh and takes newsletter sign-ups.

## Stack

Next.js 16 (App Router, `output: "export"`) · React 19 · TypeScript · Tailwind CSS v4 ·
framer-motion · SWR · markdown-it + gray-matter for the blog.

## Commands

| Command | What it does |
|---|---|
| `bun run dev` | Local dev server |
| `bun run build` | Regenerates OG images + heatmap snapshot, syncs Notion notes, then static export to `out/` |
| `bun run typecheck` | Typechecks the app and the Worker |
| `bun run lint` | ESLint |
| `bun run deploy` | Publishes `out/` to Cloudflare Pages, tagged with the commit it was built from |
| `bun run charts:refresh` | Refreshes `public/github-contributions.json` only |
| `bun run notes:sync` | Pulls published notes from Notion into `content/notes/` (add `-- --force` to re-fetch all) |
| `bun run worker:dev` / `worker:deploy` / `worker:tail` | Cloudflare Worker for the heatmap feed |

## Deployment

Full step-by-step runbook (first-time Cloudflare setup, Worker, verification, troubleshooting):
**[DEPLOY.md](DEPLOY.md)**.

```bash
bun run build && bun run deploy
```

The build script needs `GITHUB_TOKEN` (scope `read:user`) in `.env.local` so the heatmap snapshot
includes private contributions. Without it the build still succeeds and ships the last cached
snapshot.

Notes from Notion can also publish themselves: a GitHub Actions workflow syncs, builds and deploys
every 3 hours. Setup in [DEPLOY.md](DEPLOY.md#notes-publish-themselves-one-time).

## GitHub heatmap

The heatmap reads `/github-contributions.json`. In production that path is served by a Cloudflare
Worker that refreshes the data on a daily cron, so the heatmap updates without redeploying. Setup
and routing steps are in [`worker/README.md`](worker/README.md). Without the Worker the site falls
back to the build snapshot, then to a public-only API.

## Content

- Blog posts: `content/blog/*.md` (frontmatter: title, date, tags, excerpt)
- Notes: `content/notes/*.md`, synced from Notion (below). A hand-written `.md` there works too.
- Portfolio copy: `src/components/*.tsx`
- Real-me copy: `src/lib/aback.ts` (journey milestones and products), `src/components/MeHero.tsx`
  (the numbers strip under the hero)
- X sponsorship rates: `src/lib/x-rates.ts` (prices in USD; combo prices are computed from the
  items they bundle, so only the base rates need editing)
- Emails and social links: `src/lib/site.ts`
- Resume/CV PDFs: `public/resume.pdf`, `public/cv.pdf` (served from `/resume`)
- Social cards: `public/og.png`, `og-me.png`, `og-x.png`, all generated by `scripts/generate-og.mjs`

## Notes from Notion

You write notes in Notion; `scripts/sync-notion-notes.mjs` turns the published ones into Markdown
in `content/notes/` before every build, and `/notes` renders them like blog posts.

**One-time setup**

1. Create an integration at [notion.so/profile/integrations](https://www.notion.so/profile/integrations):
   type **Internal**, your workspace, capability **Read content**. Copy its secret (starts with `ntn_`).
2. Keep the notes in a Notion **database** (if they are loose pages, make a database called Notes and
   move them in). Add these properties:

   | Property | Type | |
   |---|---|---|
   | `Published` | Checkbox | Required. Only ticked notes are published; everything else stays private |
   | `Date` | Date | Optional. Defaults to when the page was created |
   | `Tags` | Multi-select | Optional |
   | `Slug` | Text | Optional. Defaults to the title, e.g. `seo-lessons-from-october` |
   | `Summary` | Text | Optional. Defaults to the first paragraph |

   A `Status` property with a `Published` option works instead of the checkbox.
3. Share the database with the integration: open it, then **••• → Connections → your integration**.
4. Copy the database link (**••• → Copy link**) and put both values in `.env.local`:

   ```
   NOTION_TOKEN=ntn_...
   NOTION_NOTES_DATABASE_ID=https://www.notion.so/...   # the link, or just the id
   ```
5. Run `bun run notes:sync`, then commit `content/notes/` and `public/notes-media/` so a build
   without Notion access still ships them.
6. Optional, and worth it: let notes publish themselves from GitHub Actions. Setup in
   [DEPLOY.md](DEPLOY.md#notes-publish-themselves-one-time).

**Day to day:** tick Published in Notion. With step 6 done, that's all: the note is live within about
3 hours, or right away from Actions → Publish notes → Run workflow. Without it, run
`bun run build && bun run deploy`. Only notes edited since the last sync are fetched again.
Unticking Published or deleting the page removes the note on the next sync. If Notion is
unreachable, the build keeps the notes it already has.

**What converts:** headings, paragraphs, bold/italic/strikethrough/inline code, links, bulleted,
numbered and to-do lists (nested), quotes, callouts, code blocks, dividers, tables, toggles, columns,
synced blocks, bookmarks, images and files. Images and files are downloaded into
`public/notes-media/<slug>/`, because Notion's own links expire after an hour. Mentions of or links to
other published notes become links on the site; links to private Notion pages become plain text.
Child pages and inline databases are skipped.

## Newsletter

Sign-up forms sit on `/me`, `/newsletter`, the blog and notes. They post to `/api/newsletter`, which
the existing Cloudflare Worker answers (`worker/src/newsletter.ts`) and stores in a KV namespace.
Bots are filtered with a hidden honeypot field and a limit of 5 attempts per minute per IP.

**One-time setup**

```bash
bunx wrangler kv namespace create NEWSLETTER --config worker/wrangler.jsonc
# paste the printed id over REPLACE_WITH_NEWSLETTER_KV_ID in worker/wrangler.jsonc

openssl rand -hex 32   # any long random string works as the export token
bunx wrangler secret put NEWSLETTER_ADMIN_TOKEN --config worker/wrangler.jsonc

bun run worker:deploy  # also turns on the devvrathans.com/api/* route
```

**Sending an issue:** the Worker only collects addresses. Export them as CSV and import the list into
the tool that sends the email (Buttondown, Resend Broadcasts, Kit, Beehiiv and so on). Use one that
adds unsubscribe links, since the sign-up copy promises one-click unsubscribe.

```bash
curl -s -H "Authorization: Bearer <NEWSLETTER_ADMIN_TOKEN>" \
  https://devvrathans.com/api/newsletter/export > subscribers.csv
```

**Local testing:** `bunx wrangler dev --config worker/wrangler.jsonc --port 8788`, then set
`NEXT_PUBLIC_NEWSLETTER_URL=http://localhost:8788/api/newsletter` in `.env.development.local` and
restart `bun run dev`. Local dev uses its own KV, never the live list.
